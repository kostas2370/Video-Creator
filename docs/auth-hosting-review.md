# Authentication and public hosting review — 14 November 2026

The current code is **not ready for public hosting without security work**. This is a focused source review, not a penetration test or a verification of a deployed host. No credentials were inspected or changed. The UI changes in this PR do not fix the findings below.

## Findings to address before release

1. **Production must reject a missing signing secret.** `backend/video_creator/settings/base.py` falls back to a known literal for `SECRET_KEY`; `production.py` does not reject that fallback. SimpleJWT uses the Django secret by default, so deploying without a unique secret can allow forged authentication tokens. Require a strong, independent production secret and fail startup when missing. The field-encryption key also defaults to a derivation of this secret; preserve the existing explicit encryption key when rotating signing keys so saved provider credentials remain readable.
2. **Add explicit CSRF validation for cookie authentication.** `CustomAuthentication` reads access cookies but does not enforce CSRF; the refresh and login endpoints also lack explicit CSRF protection. DRF API views do not gain SessionAuthentication’s CSRF checks merely from Django’s CSRF middleware. Strict auth cookies reduce cross-site exposure but do not replace CSRF enforcement, including for same-site origins. Validate tokens and origins for cookie-backed writes, including login and refresh, with regression tests for rejected unsafe requests and successful legitimate requests. Retain header-only API authentication where needed.
3. **Protect authentication endpoints against repeated attempts.** `LoginView` and `UserRegisterView` have no throttle classes, and REST_FRAMEWORK has no default throttle policy. Add shared per-account and per-source login limits, registration limits, and verify reset/verification limits. The existing contact and generation throttles do not protect login. Verify proxy trust so source limits cannot be bypassed through spoofed forwarding headers. Host-side limits were not inspected.
4. **Serve private media through an authorization boundary.** `frontend/nginx.conf` serves most `/media/` paths directly from disk without authentication; `/media/clips/` is blocked separately. Anyone with a URL can access those other media files independently of project permissions. Decide which assets may be public and use owner-authorized downloads or short-lived signed URLs for private uploads, narration, and exports. Do not assume UUID filenames provide access control. Preserve authenticated range requests for video playback and explicitly approved provider-fetch flows.
5. **Use a hardened production deployment.** The bundled Compose file publishes MySQL, Redis, and the API to host ports, contains development database defaults, and does not itself supply TLS. Restrict database/cache access to private networks, provide strong credentials, terminate TLS, configure HTTPS redirects/HSTS and trusted proxy handling, and run production settings with explicit hosts/origins. Validate the actual public host with Django’s deployment checks and external unauthenticated probes. A separate firewall or TLS proxy might supply some protections; neither was verified here.

## Existing protections

Production settings disable debug, require allowed hosts, restrict CORS to the configured frontend, and set secure cookies. Authentication cookies are HttpOnly and SameSite=Strict. Login checks email verification, access tokens expire after 30 minutes, and logout blacklists refresh tokens. Protected API routes default to authenticated access. These are useful foundations, but do not resolve the release findings above. Existing access tokens can remain valid until expiry after logout; consider shorter access lifetimes or server-side revocation if immediate revocation is required.

## Verification scope and next steps

Reviewed auth views, serializers, custom authentication, JWT/production settings, frontend clients, nginx, and Compose configuration. Did not test brute force, send cross-site requests, change live settings, run a new dependency/container vulnerability scan, inspect deployment secrets, or verify a production firewall/TLS endpoint. The older dependency-security report is historical and does not establish current safety.

After fixes, test cookie and header auth, CSRF failures, login throttling, token expiry/refresh/logout, password reset, cross-account isolation, private media and range requests. Run the complete backend suite, a fresh dependency/container audit, and `manage.py check --deploy` against the intended production configuration.
